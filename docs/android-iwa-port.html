How we got IWAs running on Android

This is a port of Chromium's Isolated Web App (IWA) runtime into an optional Helium-based Xenon Android build. A signed packaged IWA now installs and opens independently through an app-owned home-screen shim; Controlled Frame renders inside it. The work is still experimental.

Current boundary: working lab flow, not a production browser feature.

The ordinary org.agent54.xenon browser is unchanged. The experimental browser is a separate org.agent54.xenon.iwa package. Android IWA updates are explicitly blocked while window and update coordination is unfinished.

What runs when someone taps the icon

Signed bundleA .swbn is installed into the experimental browser profile in the lab.
App-owned shimA separate Android APK provides the Kitchen Sink home-screen icon.
App-ID intentThe shim passes only a fixed installed app ID, never a URL or bundle path.
Browser verificationXenon waits for its registry, verifies the installed IWA, then launches a private activity.
Isolated pageWebappActivity loads isolated-app:// content and its Controlled Frame.

The browser-owned entry refuses incomplete first run, off-the-record profiles, disabled IWA support, unknown IDs, and mismatched scope or origin. A bounded registry wait and weak activity reference avoid an unbounded launch request. The home-screen shim is deliberately small: its launcher source contains the fixed Kitchen Sink app ID and an explicit browser component.

What changed in the source

The build pins Chromium 154.0.8037.57 and Helium revisions in source.lock.json. build.sh applies Helium's patches, Xenon's ordinary Android patches, then the optional IWA patch series only when --experimental-iwa is requested. The optional build uses its own output directory, package ID, and debug-flag file.

Controlled Frame: more than making an element appear

The first Xenon build rendered <controlledframe> as an unknown element. The fix required browser, common, and renderer registration plus its Android API feature gate. That alone would have been unsafe: the boundary decision also requires an installed IWA with the Controlled Frame manifest capability, a guest partition owned by that IWA, same-origin packaged resource fetching, the existing media-consent handler, and guest cleanup.

On the Android 16 emulator, an ordinary HTTPS page and a signed IWA without the permission had no Controlled Frame element. A relative packaged script loaded; HTTPS, another IWA origin, and same-origin blob: script URLs failed without crashing the browser. Google rendered inside Kitchen Sink on the emulator, Samsung tablet, Pixel, and the Pixel's external desktop display in earlier unlocked tests.

What has actually been verified

  • The signed Kitchen Sink bundle installed in the experimental profile on the Android 16 emulator, Samsung SM-X710, and Pixel 10 Pro XL. The home-screen shim opened its WebappActivity on all three.
  • Kitchen Sink reported a secure, cross-origin-isolated context with SharedArrayBuffer on the emulator. The simpler signed Hello Xe IWA, without the policy, did not report cross-origin isolation.
  • Wrong-action and unknown-app-ID launch requests returned to the launcher without opening another IWA activity on the physical test devices.
  • Focused Java activity tests, native close/lease/coordinator tests, arm64 and x86-64 build checks, and repository tests have passed at their documented revisions. The latest coordinator suite has 11 emulator passes; it does not exercise the real update manager. Both portable IWA entitlement cases also pass on the emulator.

The patch-0056 experimental APK is installed on both physical devices. Kitchen Sink and Google's Controlled Frame visibly rendered on the tablet; the Pixel reached the IWA activity but was locked for the latest visual check. Earlier unlocked canaries showed distinct same-site ordinary/guest canvas outputs and completed bounded TCP and UDP echoes. Patches 0057–0060 have been tested on the emulator only. The update coordinator remains unwired and updates remain blocked. For hashes and exact limitations, see the running port log.

What is still missing

  1. Distribution: a user-facing signed-bundle install/uninstall experience and a general per-IWA Android shim or shortcut flow. Today's Kitchen Sink shim is fixed to one app ID, and lab installation uses a one-time developer command-line switch.
  2. Safe updates: disposable real-browser tests reproduced a lost callback, a nested-completion crash, and callbacks running after shutdown. Patches 0057–0060 address those narrow cases, including shutdown during a two-callback batch and from callback A’s captured-state destructor. A further test is still red: shutdown retains a callback for another app instead of discarding its captured state. The probes are not yet always-run. The separate coordinator and lease are not connected to the manager and scheduler; owner deletion, post-shutdown entry, persisted-startup updates, busy-app deferral without losing the staged bundle, and IWA content outside standalone activities still need tests. The current guard must remain until end-to-end update tests pass.
  3. Direct Sockets: the separate experimental patch exposes frame-owned TCP/UDP in Kitchen Sink. Emulator loopback, worker-denial, permission-denial, active-socket teardown, consent-pending navigation, and a short background/resume TCP check passed. A focused native test fixed Android's missing isolated-app content-setting pattern; a reproducible disposable-emulator fixture verified explicit BLOCK denial through the public API. Changing BLOCK denies new sockets but does not close existing ones, so production policy must state that clearly. Samsung tablet and Pixel canaries exchanged TCP and UDP echoes with this Mac after granting the experimental IWA local-network access; their Controlled Frame guests lacked the APIs. An always-run production BLOCK test, broader races, and further lifecycle checks remain before support is complete. See the Direct Sockets boundary.
  4. Screen capture: Kitchen Sink's current manifest does not request display-capture, so getDisplayMedia rejects at the policy gate. Its requested all-screens-capture policy is not enabled on Android and getAllScreensMedia is absent. Neither is a working capture test; an optional, separately reviewed capability would need consent and lifecycle checks. See the screen-capture boundary.
  5. Security coverage: restore an Android-safe subset of web-app and Controlled Frame tests currently excluded by broad desktop test gates. Verify real embedder media consent, persistent and cross-app partitions, disallowed guest schemes, context-menu cleanup, app-removal races, and ordinary-browser regressions. The original emulator probe found identical same-origin canvas fingerprints in an ordinary tab and two storage-isolated Controlled Frame guests. Experimental patch 0055 separates browser-validated guest tokens and site-exception policy. A later teardown race found a pre-attach navigation that fell back to the ordinary tab's text and font-free canvas outputs; patch 0056 addressed this in emulator checks and was upgraded on both physical devices, though the locked Pixel lacks a fresh visible privacy check. Always-run GuestView/navigation and policy regressions, owner-loss/changed-owner cases, extension WebView fallback, and applicable MPArch coverage remain. Do not allowlist HELIUM_NOISE yet. See the Controlled Frame boundary.
  6. Optional browser integration: general scheduler launch, link capture, file/protocol handling, and desktop-like OS integration are not part of this narrow independent-shim flow.

The next release decision should distinguish “a signed IWA launches and Controlled Frame renders” from “all IWA update and isolation paths are safe.” The first has device evidence; the second remains work in progress. See the update-lifecycle design gate.
